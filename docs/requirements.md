# 要件定義・データ設計(衝動代替アプリ)

> 企画・仕様の全体像は `app_concept.md`、開発の進行計画は `dev_schedule.md` を参照。
> 本ファイルは機能要件とDBテーブル設計に特化する。

---

## 1. 機能要件(MVP)

1. **認証機能**: Devise によるユーザー登録・ログイン・ログアウト。MVPでは最小限(メール認証・パスワードリセットは作り込まない)。
2. **衝動記録機能**: 衝動ボタン(連打+3-3-6呼吸、詳細は `app_concept.md` 3章)を終えると、衝動が来た記録(urge)が1件保存される。連打完了時にレコードを作成し、その後の入力で更新していく。
3. **代替行動機能**: マザーデータ(筋トレ・読書・散歩・ストレッチ等)をユーザー登録時に各ユーザーへコピーして配布。ユーザーは自分の代替行動を自由に追加・編集・削除できる。
4. **記録の可視化**: その日に衝動が来た回数を棒グラフで表示。
5. **ストリーク表示**: 衝動が来た時にアプリの衝動ボタンを開けた連続日数を表示。

## 2. テーブル設計

3テーブル構成: `users` / `alternative_actions` / `urges`

### 2-1. users(ユーザー)

Devise 標準の users に `name` を追加する程度。年齢等の属性は集めない。

| 列 | 型 | 説明 |
|---|---|---|
| id | bigint | 識別子(主キー) |
| name | string | ユーザー名 |
| email | string | Devise標準(ログインID) |
| encrypted_password | string | Devise標準(暗号化済みパスワード) |
| created_at / updated_at | datetime | Rails標準 |

※ email / encrypted_password 等は Devise が用意するもの。追加するのは実質 `name` のみ。

### 2-2. alternative_actions(代替行動)

マザーデータもユーザー追加分も**この1テーブルで管理**する(役割が同じため。使われ方=「衝動が来た時にメニューに表示される」も同一)。

**マザーデータの扱い(重要)**: 別テーブルや user_id=NULL の共有データにはしない。**ユーザー登録時に、マザーデータを各ユーザー用のレコードとして複製して配る**(流派B)。これにより全レコードが user_id を持ち、デフォルトの行動もユーザーが自由に編集・削除できる(「膝が悪いから"筋トレ"を消す」等が可能)。データ量は1人あたり数件のコピーで問題にならない。

| 列 | 型 | 説明 |
|---|---|---|
| id | bigint | 識別子 |
| user_id | bigint(FK→users) | 誰の代替行動か。マザーデータ由来も含め全レコードが値を持つ |
| title | string | 行動名(例:「筋トレ」「積んでる本の続きを読む」) |
| time_span | enum(integer) | 所要時間の区分。`immediate`(即終わる)/ `short`(少し時間かかる)/ `preparation`(準備がいる) |
| created_at / updated_at | datetime | Rails標準 |

- `time_span` の狙い: 衝動が来た瞬間に「今すぐできるもの(immediate)」から優先的に出せるようにする。

### 2-2-1. 代替行動の提案ロジック(衝動ボタン後)

衝動が来た瞬間に選択肢を大量に並べると、それ自体が「選ぶ・考える」という認知的ハードル(=このアプリが埋めようとしている"準備のワンクッション")になってしまう。よって以下の方針で提示する。

- **各 time_span から1つずつ、ランダムに提案する**(immediate から1つ、short から1つ、preparation から1つ)。
- **`immediate` を主役にする**。上から immediate → short → preparation の順で並べ、下に行くほど視覚的に控えめにする。short と preparation の手前には「時間があるなら…」のような文言を置き、"今すぐの提案ではない"ことを伝える。すぐ動きたい人の視線は自然に一番上(immediate)に落ちる。
- **その time_span に登録が0件なら、その枠ごと非表示**にする(空欄を見せると「登録して」という宿題を突きつけるノイズになるため)。マザーデータで3区分すべてに3個以上入れておくので、初期状態で枠が欠けることはない。
- 提案とは別に「**他の行動を選ぶ**」の文言を置き、押すとそのユーザーに紐づく代替行動の全一覧を表示する。面倒なユーザーは提案されたものをそのまま実行すればよく、選びたいユーザーは全一覧から選べる。
- 「選ばれた回数の多い順」提案は**採用しない**。urges は宣言(took_action)までしか記録せず実行有無は追わないため、回数が実態(効いたかどうか)と乖離するリスクがあるため。
- お気に入り機能は、必要なら alternative_actions に `favorite`(boolean)列を1つ足すだけで実装可能(中間テーブルは不要。alternative_actions は既に user_id を持ち1人のものだから)。MVPでは任意・発展扱い。

### 2-2-2. マザーデータ初期セット(確定)

ユーザー登録時に各ユーザーへコピーして配る初期の代替行動。位置づけは「こういう代替行動がおすすめだと知ってもらい、試してもらう」(実用寄り=A)。3区分すべてに3個以上あるので、ランダム提案で枠が欠けない。

**粒度の原則**: 代替行動は「読んだ瞬間に何をするか分かる」具体的な粒度にする("筋トレ"のような抽象語は「何をしよう?」という一手間=ワンクッションを生むため分解する)。ただし説明過多にはしない(「腕立て10回」で止め、フォーム解説まではしない)。preparation は「時間があるなら」の枠なのでざっくりでよい。

**immediate(即できる・その場0秒・道具なし)**
- 手をぎゅっと握って開く
- 拍手を10回思いきり
- その場で10回ジャンプする
- 冷たい水で顔を洗う
- 部屋の中を1周歩く
- 声に出して数を10まで数える

**short(少し時間がかかる)**
- 腕立て10回
- 腹筋10回
- スクワット10回
- 5分歩く
- ストレッチをする
- シャワーを浴びる
- コンビニで好きなお菓子を1つ買う

**preparation(準備がいる・ざっくり)**
- ジムで筋トレする
- サウナに行く
- 30分ランニングする
- 外に散歩・買い物に出る
- 友達に連絡を取る

※ 補足: immediate に「握る・拍手・ジャンプ」など身体を使う発散系を厚めにしているのは、開発者本人の「そわそわは指を動かすと止まる」という実感、および衝動ボタン(連打)の思想と地続きにするため。「コンビニでお菓子」は発散ではなく"小さな健全なご褒美"型のバリエーション。


### 2-3. urges(衝動記録)★このアプリの中核

**記録の起点**: 衝動ボタン(連打)完了時に1件作成する(案1)。「衝動が来た」という事実を取りこぼさないことが最優先。以降、ユーザーの入力に応じて同じレコードを更新していく。

| 列 | 型 | 説明 |
|---|---|---|
| id | bigint | 識別子 |
| user_id | bigint(FK→users) | 誰の記録か |
| resolved | enum(integer) | 状態。**デフォルト `pending`**。`pending`(未選択・連打直後)/ `calmed`(落ち着いた)/ `took_action`(代替行動へ)/ `viewed`(見てしまった) |
| trigger | enum(integer), null許容 | タイミングのトリガー(任意)。`idle`(暇な時=取りかかるべき作業がない時)/ `working`(作業中=勉強でも仕事でも)の2択のみ。「寝る前」「起床直後」等の時間帯は `created_at` から分かるため選択肢に持たない。当てはまらない/選ばない場合はスキップして null。選択画面には「スキップ可」のラベルを出すが、トリガーを選ばず次のボタンを押せばそのまま null で進める(スキップ用の余計なタップは増やさない) |
| alternative_action_id | bigint(FK→alternative_actions), null許容 | `took_action` の時に選んだ代替行動。それ以外は空 |
| memo | text, null許容 | 衝動のきっかけの自由記述(任意)。例:「ポルノ系の広告を見てしまって」。トリガー(いつ)では捉えられない"なぜ・何がきっかけで"を残す |
| created_at | datetime | **「いつ衝動が来たか」= 集計の主役**。棒グラフ(その日の回数)もストリークもこの日時から算出 |
| updated_at | datetime | 後から `viewed` に更新した時などに動く |

## 3. urge の状態遷移(resolved)

```
[連打完了]
   ↓ urgeを1件作成(resolved = pending)
[連打後の画面: トリガー選択・メモ入力(任意)]
   ↓
   ├─「落ち着いた」を押す  → resolved = calmed
   └─「代替行動を選ぶ」を押す → resolved = took_action + alternative_action_id をセット
   
[後日・別入口(任意)]
   ↓ 正直に振り返って記録する場合
   → resolved = viewed に更新(または、衝動ボタンを押さず直行した場合は
      新規に urge を作って viewed にすることも将来的に可能)
```

- **重要な思想**: `viewed` は「連打後の画面の選択肢」としては出さない。「見てしまった(過去の結果)」と「代替行動を選ぶ(未来の宣言)」は発生タイミングが違うため、同じ画面の二択にしない。`viewed` は後から状態を上書きするための受け皿として enum に用意しておく。
- `resolved` を最初から enum にした理由: 後から状態(viewed 等)を足しやすくするため。boolean だと2状態しか表現できず、拡張時に作り直しになる。

## 4. 連打後の画面レイアウト(縦比率 1:2:7)

任意入力(トリガー・メモ)を視覚的に小さくし、「スキップが自然」に見えるようにする。急いで発散したい人を邪魔しない、という設計思想をレイアウトで表現する。

```
┌─────────────────────┐
│ [トリガー選択]        │ ← 約1割。小さいチップを横並び
│ 暇 寝る前 勉強中      │   (タップで選ぶ・選ばなくてもよい)
├─────────────────────┤
│ [メモ(任意)]         │ ← 約2割。小さめの入力欄
│ 何かきっかけがあれば…  │   (プレースホルダーで"任意"感を出す)
├─────────────────────┤
│                     │
│  ┌───────────────┐  │
│  │  落ち着いた     │  │ ← 約7割。主役。大きく押しやすく
│  └───────────────┘  │
│  ┌───────────────┐  │
│  │  代替行動を選ぶ  │  │
│  └───────────────┘  │
└─────────────────────┘
```

- 上部(トリガー・メモ)は見えているが小さく、「飛ばしてよい」と直感的に伝わる。
- 下部の大きな2ボタンで、急いでいる時は上を無視して即タップできる。
- 書きたい人だけ上に指を伸ばせばよい。

## 5. viewed(見てしまった)の記録・別入口(確定)

「見てしまった」は過去の結果であり、衝動ボタンのフロー内の選択肢としては出さない(未来の宣言=代替行動選択とタイミングが違うため)。代わりに、トップ画面から入る別入口で任意に記録する。

- **入口**: トップ画面下部に「記録する」系の常設ボタンを置く(文言は実装時に詰める)。
- **2つの経路**:
  - **(A)過去の記録を「見てしまった」に更新**: 過去**1週間分程度**の記録(urge)を一覧から選び、その resolved を `viewed` に更新する。
    - 「直近1件のみ」にしない理由: 衝動が立て続けに来た場合(1回目連打→見てしまう→2回目の衝動→1回目のviewed入力前に2回目を連打…)、直近1件だと1回目を更新できなくなるため。連続した衝動は依存が強い時期ほど起こりやすい。
    - この「過去から選ぶ」画面を専用に新設するか、既存の「記録一覧」画面に相乗りさせる(各行から直接 viewed に変えられるようにする)かは、**実装時に判断**(記録一覧のUIの作り方次第。相乗りできれば画面が増えず軽い)。
  - **(B)記録せず見てしまった分を新規作成**: 衝動ボタンを押す間もなく直行して見てしまった場合、新規に urge を作成し `viewed` にする。
- **(B)新規作成時の trigger / memo**: 任意で入力できるようにする(衝動ボタン経由と同じ、連打後の入力UIを使い回す)。最小限だと `created_at` と `viewed` のみでも成立する。
- **トーン(重要)**: 全体を通して責めない。ユーザーが最も自己嫌悪を感じやすい瞬間に触れる画面なので、色・文言で追い詰めない。「記録しました」と淡々と受け止める(`app_concept.md` の記録の思想と一貫)。

## 7. ストリークの算出ロジック(2026/08/13 確定)

数えるものは `app_concept.md` 3章(4)の通り「衝動が来た時にアプリの衝動ボタンを開けた日」の連続日数。
算出は `urges.created_at` のみを使う。

- **`resolved` を問わず、すべての urge を数える。**`viewed` を除外しない。
  除外すると「正直に『見てしまった』と記録した瞬間に連続が切れる」構造になり、**記録すること自体が罰**になる。
  これは「責めない」(`design_guideline.md` 原則2)に正面から反する。
  よって「見てしまったと記録した日も、アプリに手を伸ばした日として数える」。
- **今日の記録がまだ無い場合は、昨日を起点に遡って数える。**今日を「未確定」として扱う。
  日付が変わった直後に「0日」を見せないため。
- 日付は必ず `in_time_zone` を通して JST で判定する(`CLAUDE.md` §9)。
- **既知の割り切り**: 衝動が来なかった日も記録が無いので連続は切れる。
  記録が無い以上「来なかった」と「開けなかった」は区別できないため、MVPではこれを受け入れる。
  README と発表でこの数え方を選んだ理由として説明する。
