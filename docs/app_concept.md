# 衝動代替アプリ 企画書

> このドキュメントは、プログラミングスクールの発表会(期限: 1ヶ月弱)に向けたアプリ企画の記録です。
> 別セッションのClaudeがこれを読んだ場合、以下の内容を前提として、すぐに設計・実装のサポートに入れる状態を目指しています。

---

## 1. 背景・課題感(開発者本人の実体験)

- SNS、ポルノ、タバコなど依存性の高いものを、頭では「やめたい」と思っていてもやめられない経験がある。
- トリガーは主に「暇な時」「寝る前」「勉強中のストレスがかかった時」。行動直前には「体の奥がムズムズする」「そわそわして落ち着かない」という身体的な衝動の感覚がある。
- 過去、運動・筋トレ・読書によって一時的に依存対象を絶てていた時期があった。しかし以下の理由で崩れた:
  - 「ご褒美として1日くらいいいだろう」とパチンコに行ったことがきっかけで、そこからずるずる戻ってしまった。
  - 夜に読む本のストックがなくなり、代わりに動画を見るようになった。
- **本質的な原因の自己分析**: 「意志力の問題」ではなく、「刺激の即効性・アクセスのしやすさの非対称性」が原因。
  - SNSやポルノは指一本、0秒で強い刺激が得られる。
  - 読書や筋トレは、準備(本を探す、着替える等)のワンクッションがあり、しかもすぐには盛り上がらない。
  - この非対称性こそが、継続できない一番の理由。
- タンパク質・カロリー計算の面倒さも当初のアイデアとして出たが、既存アプリ(あすけん等)で代替可能であり、テーマとしての独自性が薄いため**不採用**。依存系テーマに一本化した。

## 2. アプリテーマ(確定)

### 「刺激の即効性ギャップを埋める、衝動代替アプリ」

**コンセプト**: 依存対象(SNS・ポルノ・タバコ等)が強いのは「0秒で強刺激が来る」から。だから代替行動も「0秒で始められる」形に事前に用意しておけば、誘惑に勝てる確率が上がる、という仮説に基づいたアプリ。

**基本フロー**:
1. 衝動(そわそわ・ムズムズ)を感じたら、SNSやポルノを開く代わりにこのアプリを開く。
2. アプリ内で衝動を発散させる(連打しながら3-3-6呼吸を36秒。詳細は3章)。
3. 「落ち着きましたか?」と尋ね、YES→元の作業に戻る/NO→代替行動メニューを提示。
4. 代替行動を実行、または我慢の成否を記録。
5. 記録が蓄積され、可視化・ストリーク表示によって自己理解と継続動機を強化する。

## 3. 既存アプリとの差別化ポイント

既存の依存対策アプリ(Forest、Opal、BetterMe等の「禁欲アプリ」「習慣トラッカー」系)は、著者の過去の利用経験では試したことはないが、一般的に「通知」「アプリを開くのを止める」「スマホを触らせない」という**制限・我慢させる**アプローチが主。

このアプリは逆に、**代わりに触る・代わりの行動を提案する・記録する**という「発散・代替」アプローチを取る。

| 観点 | 既存アプリ | このアプリ |
|---|---|---|
| アプローチ | 我慢させる(制限・通知・ブロック) | 発散させる(衝動ボタンで逃す) |
| 継続の仕組み | 意志力に頼る | 代替行動を事前登録し、準備コストをゼロにする |
| 終わり方 | ブロックして終わり | 記録して自己理解を深める(自分の危険なタイミングが見える) |

### 差別化ポイントの詳細設計

**(1) 衝動ボタン(発散の仕組み)= 連打しながら3-3-6呼吸**
- 衝動を感じたらボタンをタップ→**連打しながら、同時に3-3-6呼吸(3秒吸う・3秒止める・6秒吐く)を行う**。この呼吸を3セット=合計36秒間繰り返す。連打は「サンドバッグ」的に身体的な衝動(指を動かしたい感覚)を発散させ、呼吸は理性を取り戻させる。
- **「連打と呼吸を同時に行う」ことの理由(重要)**: 当初は「連打→その後に深呼吸」の2段階を検討したが不採用。ドーパミン依存の状態にある人は、たった10秒でも「何もしていない空白の時間」に耐えられず、その隙にアプリを閉じて離脱するリスクが高い。呼吸中も手を動かし続けられるよう、連打と呼吸を同時に行う設計にした。連打の労力そのものがドーパミンの代替になり得るという狙いもある。
- **重要な設計判断(数値化・過剰刺激の排除)**: 連打の回数やスコアは一切表示しない。回数を見せると「今日は100回押せた」のような新しい依存・ゲーム化のループを作ってしまうため。感覚的フィードバック(強い振動・派手な音・派手なアニメーション)も過剰にしない。フィードバック自体が新しい快感・依存の芽になり得るため、無機質で煽らない表現に徹する。
- 36秒経過後、「落ち着きましたか?」とYES/NOで尋ね、状態を自己申告させて分岐する(一律に次のステップを押し付けない)。
  - YES → 元の作業に戻る
  - NO → 代替行動メニューへ

**衝動ボタンのアニメーション詳細(呼吸フェーズごと)**

モチーフは「赤い円」。表情のない無機質な見た目で、煽らないことを最優先する(当初は3Dの人体模型キャラ案もあったが、three.js等での3Dモデリング・アニメーションは1ヶ月弱では実装コストが重すぎるため不採用。円のCSS/SVGアニメーションで同じ「無機質・煽らない」狙いを達成する)。

- **吸う(3秒)**: 赤い円が広がる。ユーザーは**最速で思い切り連打**する。連打に応じて、赤い円の中に黄色い線の円が広がって見える(※演出上そう見せるだけで、実際には連打数と広がりは無関係。数値報酬を与えないという原則を守るため)。
- **止める(3秒)**: 円のサイズは止まる。連打すると、ゴムボールを殴った時のように、叩いた部分だけが「ポヨン」と揺れる。息を止めている=全体の動きは止まっている中で、タップの手応えだけが静かに返る。
- **吐く(6秒)**: 赤い円が、**こちらが指定したゆっくりめのテンポ**で縮んでいく。主導権がユーザー(自由な発散)からシステム(制御された鎮静)へ移るフェーズ。
  - テンポの提示方法は**鼓動型**: 円自体が指定テンポでわずかに脈打ち、その脈に合わせてユーザーがゆっくりタップする。
  - タップへの視覚的な手応えは吸う時より控えめにし、6秒の後半にいくほどさらに静かに、反応がフェードアウトしていく(「もう連打しなくて大丈夫」という状態へ身体的に着地させる)。速く叩いても反応は増えない(勢いに報酬を与えない)。
  - 狙い: 36秒全体が「興奮のピーク(吸う・連打)→鎮静(吐く・フェードアウト)」へと綺麗に着地し、直後の「落ち着きましたか?」にYESと答えやすくなる。

**(2) 代替行動メニュー(準備コストゼロの仕組み)**
- 事前に登録しておいた「効果のある行動」を、衝動が来た瞬間にワンタップで提示する。
- 過去の実体験(読書・筋トレで一時的に成功していた)から、「効果がある行動は人によって全く違う」「自分で言語化しておく(実行意図: implementation intention)こと自体が行動の実行率を上げる」という理由で、**マザーデータ(筋トレ・読書・散歩・ストレッチ等の一般的な候補)を用意しつつ、ユーザー自身が自由入力でカスタマイズできるハイブリッド方式**を採用する。
- 理想的には「読書」ではなく「今読んでる本の続きのページを開くだけ」まで個人が作り込めると、摩擦がさらに減る(MVP以降の発展余地)。

**(3) 記録・可視化 = 「宣言ベースの自動記録」+「任意の振り返り記録」**

記録の思想: **アプリはユーザーを監視も採点もしない。ただ、自分を見つめたい人のために"入口"だけは用意する。** 強制しないからこそ正直に記録できる、というスタンス。「煽らない・数値で報酬を与えない」設計思想と一貫させる。

- **なぜ成否を判定しないのか(重要な設計判断)**: 「代替行動を選ぶ」のは"これから何をするか"という**未来の宣言**であり、「見てしまった」は"結局どうなったか"という**過去の結果報告**。この2つは発生するタイミングが異なるため、同じ画面の二択にすると時系列が破綻する。また、衝動ボタンを押した時点では成否はまだ確定していない(「筋トレする」と宣言してもその後やらないこともある)。よって、1回のセッション内で成否まで判定しようとせず、**「衝動ボタンを押せた=それ自体が小さな前進」と捉えて成否判定を手放す**。

- **自動的に残る記録(宣言ベース)**:
  - 衝動が来てボタンを押した日時
  - 「落ち着きましたか?」への回答(はい/いいえ)
  - いいえの場合、どの代替行動を選んだか
  - ここまでで記録は一旦完結。成否は判定しない。

- **任意で残せる記録(振り返りベース・別入口)**:
  - ホーム等に「見てしまったことを記録する」導線を常設する。
  - 衝動ボタンを押す間もなく直行して見てしまった時も、事後に正直に打てる。
  - 打っても打たなくてもアプリは正常に機能する。打てば自己理解の材料が増える、という位置づけ。
  - **トーン**: 「見てしまった」を打っても責めない。「記録しました」と淡々と受け止めるだけ。責めるUI(赤字の警告、派手なリセット等)にすると記録するのが嫌になりデータが集まらなくなるため。

- **可視化(棒グラフ)**: 主軸は「**その日に衝動が来た回数**」。成否のような評価を含まないため、ユーザーを採点せず「自分のパターン」だけを淡々と映せる。グラフが減れば結果的に励みになり、減らなくても責められている感じがしない。
- 当初は時間帯・曜日別ヒートマップも検討したが、開発コストとデータ量不足(短期間では有意な傾向が出にくい)のリスクから、MVPでは見送り、発展機能とする。

**(4) ストリーク表示**
- **数えるもの**: 衝動が来た時に(見てしまう前に)アプリの衝動ボタンを開けた日。
- **単位**: 連続日数(今続いている連続だけを表示する)。
- **意味**: 「悪い刺激(SNS・ポルノ等)の代わりに、このアプリに手を伸ばせた」連続日数。伸びるほど自己肯定感につながる。依存の仕組みを敵視せず、"良い方向(=衝動ボタンを開く健全な行動)"に向け直すという発想。アプリの根幹「刺激の代替」と一貫している(悪い依存の代わりに無害な依存を差し出す)。
- **途切れた時の扱い(重要)**: 「責めない」思想を守るため、途切れても静かに扱う。
  - やらないこと: 「0にリセット!」と赤字で大きく見せる、通知で「途切れました」と突きつける(罰になり、記録が嫌になる)。
  - やること: 途切れたら「また今日から進めましょう」くらいの優しいトーンで促し、淡々と数え直す。
  - **最高記録は残さない**。過去最高を見せると、それ自体がハードル・プレッシャーになり得るため。今続いている連続だけを地道に表示する。
- 過去の「1日だけ」の再発(パチンコのエピソード)がどれだけコストだったかを振り返れる画面も、余裕があれば用意する。

## 6. 技術スタック(確定)

開発者のスキル前提: Rails 学習歴7ヶ月。基本的なMVCは理解している。一人で作り切る自信はまだないため、**慣れたRailsで確実に完成させることを最優先**する(新技術の習得と制作の二重負荷を避ける)。今回のアプリは認証・DB・記録集計といったサーバー側処理が中心で、Railsの得意領域と合致している。

| 領域 | 採用技術 | メモ |
|---|---|---|
| フレームワーク | **Ruby on Rails**(MVC / ERB) | 画面の大部分(認証・記録一覧・棒グラフ・代替行動登録など)は素のRailsで作る。学んできたそのままの世界 |
| 認証 | **Devise**(gem) | 定番。MVPでは最小限(登録・ログイン・ログアウト)だけ使う。メール認証(confirmable)やパスワードリセットまでは作り込まない(4章・MVP除外方針と整合) |
| DB | **PostgreSQL** | 日時での集計・グルーピングに強く、発展機能のヒートマップとも相性が良い。多くのデプロイ先が標準サポートし、開発と本番でDBを揃えられる |
| スタイル | **Tailwind CSS** | 開発者は使用経験あり。`tailwindcss-rails`等で導入。ただし後述のアニメーションは Tailwind だけでは足りず、カスタムCSS(`@keyframes`)で補う |
| 画面遷移 | **Turbo(Hotwire)** | 下記「Turboの使い分け」参照。全部使おうとせず、Turbo Frames を1〜2箇所モノにするのを学習目標にする |
| 動的な動き | **Stimulus**(+必要なJSライブラリ) | 衝動ボタンのアニメーション、棒グラフ描画など。開発者はStimulus使用経験あり |
| グラフ描画 | **Chart.js 等のJSライブラリ**(Stimulus経由で呼ぶ) | 棒グラフ(その日の衝動回数)の描画に使う |

### Turbo の使い分け(重要な整理)

Turboは3層に分かれる。今回は全部使おうとせず、費用対効果で線引きする。

- **Turbo Drive**: リンク/フォーム送信を自動でページ全体リロードなしにする。Railsでデフォルト有効。**意識せず恩恵を受けるだけでOK**(ログイン・記録一覧・ストリーク表示など大半はこれで足りる)。
- **Turbo Frames**: ページの一部だけを差し替える。**「リダイレクトを減らしてアプリっぽくする」の主役**。今回は**代替行動の登録・削除まわりで部分導入**する(一覧の一部だけ更新)。ここが投資対効果が高く、Turbo理解も深まるので、今回の学習目標に据える。
- **Turbo Streams**: サーバーから複数箇所を同時書き換え。リアルタイム用途向け。**今回は不要**(オーバースペック。時間を溶かすリスクがあるので手を出さない)。

### 衝動ボタンのアニメーションは Turbo ではなく Stimulus の担当(勘違い注意)

- Turboは「サーバーとやり取りして画面を差し替える」技術。一方、衝動ボタンの連打・呼吸アニメーションは**サーバーと通信せず、ブラウザ内で完結する**(指を動かすと円が膨らむ・脈打つだけ)。これは**Stimulus(JavaScript)+ CSSアニメーションの領域**。
- 3秒/3秒/6秒の呼吸フェーズをタイマーで管理し、CSSクラスを付け替えて円を膨らませる/脈打たせる/フェードアウトさせる、というStimulusコントローラを書くイメージ。Tailwindだけでは表現しきれない部分は `@keyframes` 等のカスタムCSSで補う。

### 画面・機能ごとの技術担当(一覧)

| 画面・機能 | 担当 |
|---|---|
| ログイン・サインアップ | Devise + Turbo Drive(自動) |
| 代替行動の登録・削除 | Turbo Frames(部分更新) |
| 記録一覧の表示 | Rails(ERB) + Turbo Drive |
| 棒グラフ(その日の衝動回数) | Stimulus + Chart.js |
| 衝動ボタン(連打+呼吸アニメーション) | Stimulus + カスタムCSS(サーバー通信なし) |
| ストリーク表示 | Rails(ERB) + Turbo Drive |

### PWA化についての方針

以前「PWA化(ホーム画面に追加してアプリっぽく使う)」を挙げていたが、厳密なPWA(オフライン対応等)まで作り込むと手間がかかる。**MVPは「スマホのブラウザで快適に使えるレスポンシブなWebアプリ」までとし、PWA化は発展扱い**とする。
