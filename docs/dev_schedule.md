先に地味だが確実に動くアプリを完成させ、アニメーションは最後の「盛り」として作る。
最悪アニメーションが簡易版(円が膨らむだけ)でもアプリとして成立する状態を先に作る。

**この「待ち時間」を、余裕のある Day 2 に置くか余裕のない Day 6 に置くかの差**である。

以後は「1機能マージ = 1デプロイ」になり、本番が壊れても直近1機能分の差分だけ疑えばよくなる。

## テスト方針(2026/08/07 決定)

システムスペックは採点対象であるとは確認できていないため、**二段構え**とする。

- **6日間の本線に入れるもの**: `rspec-rails` + `factory_bot_rails` のみ(Day 1・30分)。
  以後、model spec を機能ごとに数本(enum / ストリーク算出 / マザーデータ配布)。
  Day 1 に入れる価値は「テストを書くこと」より **`rails g` の出力先が変わること**にある。
  後から入れると `spec/` が空のまま放置される。
- **バッファ日に回すもの**: `capybara` + `selenium-webdriver` + 既存 chrome コンテナの配線、
  および主要導線の system spec。
- 達成できなかった場合は README に「システムスペックは今後の課題」と明記する。

`CLAUDE.md` §4 のシステムスペック方針は「バッファ日の目標」として維持する。

## 前倒しできた場合の進め方

**原則: チェックポイント到達までは、余った時間を必ず「次のコア機能」に使う。上積みは一切前倒ししない。**

理由: 切ったものは全部「溶けやすいから切った」もの。前倒しで得た1時間を、
時間が溶けると分かっているタスク(Turbo Frames・アニメーションの作り込み)に投じると、
その日のうちに前倒し分を失って遅れに転じる。
**「発表できる状態」に着く前は、どんな機能よりバッファ1時間のほうが価値が高い。**

### チェックポイント**到達前**に時間が余ったら(この順で)

1. **次のスライスに進む**(Day 4 の完了条件を前に引き寄せる)
2. まだ余るなら **README を書き始める**(Day 6 の項目。低リスクで、発表資料の下書きも兼ねる)
3. まだ余るなら **休む**。前倒しできた日に休むのは正解であって怠慢ではない。
   solo で10日走り切って発表当日にガス欠になるほうが、機能1つ足りないより痛い。

### チェックポイント**到達後**に時間が余ったら

バッファ日の積み残しリスト(上記)を**上から**消化する。
すなわち リハーサル → system spec → Turbo Frames → アニメーション磨き込み の順。

### 前倒し時にやってはいけないこと

- **「ついでにここも綺麗にしておくか」でスコープを広げない。** 前倒し分はバッファであって、予算ではない。
- **アニメーションを Day 3 のうちに作り込まない。** 衝動ボタンを触っている流れで凝りたくなるが、
  これが旧計画から一貫して警戒している最大の時間溶かしポイント。**Day 6 まで簡易版で固定する。**
- **日付を繰り上げて「Day 5 を今日やった」と数えない。** チェックポイントへの到達だけで進捗を測る。

## リカバリー方針(遅れた時の削りどころ)

**下の「削るリスト」と、上の「前倒し時に積むリスト」は同じものである。**
遅れたら上から削り、余ったら下から積む。1本のリストを両方向に読む。

優先度の低い順に諦める:

1. 呼吸アニメーションの作り込み → 簡易版(円が膨らむだけ)に落とす
2. Turbo Frames での部分更新 → 通常のページ遷移でも機能は成立する
3. ストリーク表示 → 棒グラフがあれば自己理解の機能は成立する
4. 「見てしまった」の任意記録 → 発展扱いに回す

※ **認証・代替行動CRUD・衝動記録・棒グラフの4つは中核なので死守する。**

## 既知の地雷(2026/08/07 調査で判明。Day 1〜2 で潰す)

| # | 内容 | 対処日 |
|---|---|---|
| 1 | **Tailwind v4 が `app/views/` をスキャンしていない**。`app/assets/builds/application.css` は 4.5KB でユーティリティが実質ゼロ。クラスを書いても効かない。→ CSS に `@source` を明示 | Day 1 |
| 2 | **`stylesheet_link_tag :app`** が cssbundling の出力(`application.css`)と噛み合っていない可能性 | Day 1 |
| 3 | **`TEST_DATABASE_URL` を Rails は自動では読まない**。`config/database.yml` の test は `app_test` ベタ書きで、`DATABASE_URL` が上書きされる。**テストが開発DBを消しうる**。`CLAUDE.md` §4 の「分離済み」は現状成立していない | Day 1 |
| 4 | **production の database.yml が 4DB構成**(primary/cache/queue/cable)。Neon(DB1個)では起動時に落ちる | Day 2 |
| 5 | **Stimulus は手動登録制**。`app/javascript/controllers/index.js` に import + register を書かないと「エラーも出ず何も起きない」 | 都度 |
| 6 | Rails 8.1 で enum のキーワード記法は削除済み。位置引数形式のみ | 都度 |
| 7 | タイムゾーン未設定。UTC のままだと朝の記録が前日扱いになり、棒グラフとストリークが静かにずれる | Day 1 |
| 8 | **Puma がコンテナ内 localhost にしかバインドしない**。Rails 7.1 以降 development の既定が `127.0.0.1` になったため、`3200:3000` のポート公開が届かず localhost:3200 が開けない。→ `Procfile.dev` に `-b 0.0.0.0` | Day 1 済 |
| 9 | **開発DBが未作成**。`db:create` が一度も走っておらず全リクエストが500になる。→ `db:prepare` | Day 1 済 |

※ `yarn.lock` の linux-x64 エントリは確認済み(21件)。Render とのプラットフォーム差の問題は起きない。

## メモ

- 各機能の完了時に、実際にブラウザで触って確認する。動く状態を常にキープするのがバッファの薄い今回の生命線。
- main へのマージは開発者自身が行う(`CLAUDE.md` §8)。マージ = 本番デプロイ。
- **発表当日は開始5分前に本番URLを1回開いて温めておく**(Render 無料枠は15分でスリープし、
  コールドスタートに約50秒かかる。Neon も5分アイドルでサスペンドする)。
